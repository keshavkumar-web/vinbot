## Release — 2026-07-01 (comparison follow-ups — deterministic & grounded)

**Gap + safety catch:** "Compare Ambala and Karnal" → two totals, then "Which is
higher?" clarified ("what total?") instead of comparing. While fixing it I found
that routing a comparison through the LLM let it **fabricate** the two figures
when they weren't in the history (correct by luck, but an invented number — a
hard-requirement violation).

**Fix:** comparison follow-ups are answered **deterministically from the values
already shown**, never by the LLM. `followup.is_comparison_question` detects
"which is higher/lower/largest?", "what's the difference?", "how much more?"
(conservative — NOT a broad new query like "which district has the most?").
`followup.compare_from_history` extracts the `Entity — Metric: value` facts from
recent answers (which came from SQLite), compares/ranks them in Python, and — for
"difference" — subtracts exactly. If there aren't ≥2 comparable values in the
history it returns the standard not-found line rather than guess. The number is
never re-generated by the model.

Also: `intent.py` — a bare "Compare A and B" now defaults to the "Total" column
per entity (was intermittently clarifying), so the compare→"which is higher?"
flow holds end-to-end.

Example: Compare Ambala and Karnal → "Which is higher?" → *"Karnal (543,445) has a
higher Total than Ambala (394,560)."*

Refinements (all in `compare_from_history`/`compare_facts`):
- **Drop the utility-wide aggregate** ("Grand Total") when ≥2 specific rows are
  present — comparing a district to the grand total is meaningless.
- **Self-contained comparisons** ("which is greater between A and B for
  domestic?") now work on the first turn: no history, so `chat` does a fresh
  `tables.respond` lookup and compares the returned facts. `intent.py` rule 4
  returns one selection per named entity for a comparison (was clarifying).
- **Subject-aware**: when both connection *and* load totals are in scope, "which
  has more LOAD?" compares the KW figures, "which has more connections?" the
  counts — `compare_facts` filters facts by the question's subject word against
  each fact's metric/unit/source/dataset (de-pluralised match, so "connection"
  hits 1_Connection.pdf but not 2_Connected_Load.pdf). Previously it grouped by
  the most-common metric+unit and ignored the word "load".

**Files:** `app/followup.py`, `app/chat.py`, `app/config.py`, `app/intent.py`,
`eval_followup.py` (Part C comparison guard). **Validation:** `eval_followup`
13/13, `eval_tables` 18/18, `eval_intent_live` 18/18, `validate_e2e` 19/19 (0% FP).

## Release — 2026-07-01 (follow-ups must keep the dataset/subject)

**Bug:** in a CONNECTIONS conversation, a bare metric follow-up jumped datasets —
"Now Zone-I" → Zone-I Domestic connections (1,314,372, 1_Connection.pdf), then
"total?" → Zone-I Total **connected load** (7,395,321 KW, 2_Connected_Load.pdf)
instead of Zone-I Total **connections** (1,751,105). The rewriter dropped the
subject ("total?" → "Total in Zone-I …"), and bare "total in Zone-I" is ambiguous
so the stateless router picked connected-load.

**Fix (`followup.py` rule 1 + example):** the contextualiser must carry the
SUBJECT (what is being asked about — "connections", "connected load",
"transformers damaged", …) across a metric-only follow-up, swapping only the
metric. "total?" after a connections answer → "total connections in Zone-I" →
correct 1,751,105. Verified stable ×3; `eval_followup` gained a guard case (Part B,
asserts 1,751,105 and NOT 7,395,321) → now **12/12**.

## Release — 2026-07-01 (meta-questions about our own answers)

**Gap:** the bot couldn't answer questions about its OWN previous reply —
"Which count is this?", "where did that come from?", "is that domestic or total?"
returned "I could not find this information", because the hardened prose prompt
(rightly forbidding invented figures) also blocked *restating* a figure already
given, and the numeric router even mis-clarified "is that domestic or total?".

**Fix:** a dedicated meta path. `followup.is_meta_question` detects a
back-reference to the conversation (conservative — matches "is that…", "that
number", "you said", "the source", "repeat that", but NOT ordinary follow-ups
like "and for Jhajjar?"). When it fires (and there is history), `stream_answer`
bypasses SQLite and RAG and answers from the **conversation history** under
`META_SYSTEM_PROMPT`: it may restate/explain the row/column/unit/period/source of
a value it already gave (those came from SQLite), but must never invent a new one;
if the history lacks the asked value it returns the standard not-found line.

Example: "Count in Ambala" → "Ambala — Total: 394,560" → "Which count is this?" →
*"This is the Total connection count for Ambala as of March 2026 (from
1_Connection.pdf)."*

**Files:** `app/config.py`, `app/followup.py`, `app/chat.py`, `eval_followup.py`
(new Part C). **Validation:** `eval_followup` 11/11 (incl. 3 meta cases);
`eval_tables` 18/18, `eval_rag` 4/4, `validate_e2e` 19/19 (0% FP).

## Release — 2026-07-01 (role / designation question handling)

Better semantic handling of role/designation questions in the prose path — a
retrieval fix and a prompt fix (the "never guess a designation" rule was too
blunt, treating "what is this role?" like "who holds this post?").

- **Retrieval (`rag.expand_query`):** dense embeddings don't match opaque
  abbreviations, so "who is SDO Operations" retrieved nothing about the role.
  A domain glossary now appends full forms before embedding (SDO→Sub-Divisional
  Officer, XEN→Executive Engineer, FGRA/SGRA/CGRF, ACD, LPS, OA, DTR, NDS…), so
  the role's definition surfaces. Generic vocabulary; no entity hardcoded.
- **Prompt (`config.py` rule 3b), four behaviours:**
  1. A role/abbreviation question ("who is SDO Operations", "what is XEN/FGRA")
     is answered as WHAT the role is (full form + function), grounded — not as a
     person lookup.
  2. Generic "designated officer" (no service) → clarify *"Please specify the
     service (e.g. new connection, shifting of meter, change of name)"* instead
     of not-found.
  3. Designated officer for a named service → grounded if present (e.g.
     provisional-billing → "Commercial Assistant (CA)").
  4. Still NEVER guesses a designation; a person's name or a truly-absent role →
     "I could not find this information in the knowledge base."

**Files:** `app/rag.py`, `app/config.py`. **Validation:** the four behaviours
verified live; `eval_tables` 18/18, `eval_rag` 4/4, `validate_e2e` 19/19 (0% FP).

## Data + retrieval — 2026-07-02 (RTS Act ingested → designated officers per service)

Closes the long-standing KB gap: the designated-officer-per-service schedule
(Right to Service Act) wasn't cleanly in the KB, so those questions clarified or
(worse) mis-read the officer.

- **Structured ingest (`add_rts_act.py`)** — parses `RTS_Act.pdf`'s 7-column
  schedule into LABELLED sentences ("… Designated Officer is JE [In charge]; First
  Grievance Redressal Authority is SDO[OP]; … time limit 21 days"), one per
  service/voltage, distinguishing a) meter-shifting from b) line-shifting. Avoids
  the positional-table column-confusion (the same class of bug as Domestic-vs-
  Total). APPENDS to `knowledge_db.pkl` incrementally & idempotently (never
  re-embeds the corpus; never copies dev's pkl over prod's). Run on each machine.
- **Lexical RTS retrieval (`rag.find_rts_chunks`)** — an officer/service query
  injects the matching RTS row(s) (they don't always out-rank compendium prose).
- **Prompt precedence (`config.py` rule 3b)** — an explicit "Designated Officer is
  X" line is authoritative; do NOT substitute the officer who "carries out" the
  work or the appellate authority.

Result (verified): shifting of meter → **JE (In charge)**; new connection / change
of name / reduction / reconnection → **SDO (OP)**; generic "designated officer?"
→ asks the service. **The LLM never picks the officer — the labelled row states it.**

**Files:** `add_rts_act.py` (new), `RTS_Act.pdf` (new), `app/rag.py`, `app/config.py`,
`eval_rag.py` (+RTS guard). **Deploy:** ship these, then RUN `python add_rts_act.py`
ON PROD (its KB differs from dev's), then restart. **Validation:** eval_rag 7/7,
plus 6/6 designated-officer checks; full suite green.

## Release — 2026-07-02 (customer UAT fixes)

Three issues from a customer test session (natural phrasing found what the
assertion suites missed):

1. **Figure recall inconsistency** — "how much security deposit will I have to
   pay?" returned "could not find" (and "what's the meter testing cost?" gave no
   amount), even though the figures are in the KB. Cause: with TOP_K=5 the
   descriptive chunk retrieved but the amount/table chunk didn't. Fix:
   `rag.expand_query` gained consumer-phrase synonyms ("security deposit" ->
   "Advance Consumption Deposit"; "meter test/tested/testing fee" -> "Meter
   Inspection and Testing Charges Single Phase Rs per meter") + TOP_K 5 -> 8.
   Now returns Rs. 750/KW (ACD) and the Rs. 100/200/750/1500 meter-fee table.
2. **Back-reference follow-up** — "how many of those are domestic?" (after a
   total-connections answer) mis-fired the self-contained guard and clarified.
   Fix: `followup.is_self_contained` now yields to back-reference cues
   (those/them/these/of those…) so the turn is contextualised -> 3,003,464.
3. **Jargon leak** — a clarify read "Which dataset are you referring to…". Fix:
   `INTENT_PROMPT` instructs clarify_reason in plain language (no
   "dataset"/"metric"/"column"; give examples instead).
4. **Superlative / argmax across rows** — "which circle has the maximum damaged
   transformers?" clarified (metric ambiguity) and, even after answering, had no
   way to rank all districts, so it LOOPED. Fix: `INTENT_PROMPT` treats a
   superlative as resolvable (dataset + aggregate metric + entity=null, no
   clarify); `tables._superlative_answer` ranks all NON-aggregate rows (excludes
   Grand Total / "Total …" subtotals / zones) and returns the top/bottom
   deterministically. E.g. "which circle has the most damaged transformers?" ->
   "Karnal Rural … (5,193)"; "most connections?" -> "Karnal … (543,445)"; "least
   …" -> min. Numbers ranked in Python, never generated by the LLM.

5. **Organisation identity** — "what is UHBVN?" returned "could not find" (the
   hardened no-ungrounded-facts rule refused a basic identity question the bot
   obviously knows). Fix: `config.py` rule 1a — the assistant may always state
   what UHBVN / DHBVN are and expand well-known abbreviations, even without
   retrieval. Bounded to org identity; specific figures/designations still require
   grounding (verified: "GDP of France" and an ungrounded tariff still refused).

6. **Segregation / breakup** — "segregation on connection type" (and "breakup",
   "category-wise", "split", "bifurcation", "by type") returned the Total again
   instead of the category split — worse as a follow-up, where the previous
   turn's "Total" metric was inherited. Fix: `tables.py` `_SEGREGATION_RE` +
   `_segregation_answer` list EVERY category column (Domestic, LT NDS, HT
   Industry, …) except the aggregate Total, biggest first, for the resolved
   entity; `intent.py` routes such a request to the dataset without clarifying.
   Deterministic (columns read from SQLite). Verified end-to-end as a follow-up
   after "total connection count" -> Domestic 3,003,464, LT NDS 449,105, … (not
   the Total 3,892,250).

7. **Row-wise breakdown** — "circle wise number of connections" collapsed to the
   single Grand Total (3,892,250) instead of listing each circle. Fix: `tables.py`
   `_ROWWISE_RE` + `_rowwise_answer` list the metric for EVERY circle/district row
   (largest first) for "circle/district/region wise", "each/every/per/by circle",
   "across circles"; "zone wise" lists the zone subtotals instead. Works for any
   metric ("circle wise domestic connections"). Deterministic (rows from SQLite,
   aggregates excluded). E.g. -> Karnal 543,445, Sonipat 503,067, … Panchkula
   195,820.

8. **Unknown-place safety (false-positive)** — "connections in Mumbai as of March
   2026" served the Grand Total because the trailing month "March" (a known word)
   defeated the unknown-place guard in `find_entity`. Fix: strip time/grammar
   words from the location phrase BEFORE the unknown-word test, so a trailing
   date can't rescue an unrecognised city; domain words still prevent a false
   refusal. Now Mumbai / Gurugram / Delhi all clarify instead of serving a number.

9. **Deterministic conversational slots** — a follow-up chain could drop the
   pinned dataset/metric because the LLM rewriter is non-deterministic. Worst
   case: "Domestic → Total → Load → Breakup" gave the CONNECTION breakup (counts)
   instead of the connected-LOAD breakup (KW). Fix: `followup.resolve_followup`
   recovers the active dataset / entity / metric from the last grounded answer's
   provenance lines and updates ONLY the dimension the new message names ("Total?"
   → metric, "Zone-I?" → entity, "Load?" → dataset, "Breakup?" → segregation),
   routing the result deterministically (`chat.py` runs it before the LLM path).
   Conservative: an ambiguous fragment ("Urban") defers to the LLM, so it can only
   add correct answers, never regress. Fixes the reported chains
   (Domestic→Total→Zone-I keeps Total; segregation after a Total returns the
   breakup; Load→Breakup stays in KW: Domestic 591,257 KW not 295,224).

10. **Slot machine hardening (2nd UAT round)** — the deterministic slot layer was
    too eager and mis-resolved several follow-up chains. Fixed as a set:
    - 🔴 **Safety**: an unknown place after a grounded answer ("Connections on
      moon") inherited the stale row and served a real number. Now the slot path
      detects an unrecognised place and defers, so the `find_entity` guard refuses.
    - **Column match**: a bare "Domestic?" picked "Bulk Supply Domestic". `_top_scoring`
      now prefers the column whose own tokens are fully covered → "Domestic".
    - **Entity match**: "Zone-I total" resolved to the prior circle (the extra word
      broke the tokenizer). `_entity_in` now scores by matched-token length →
      Zone-I beats Zone-II.
    - **Dataset switch**: "Damaged transformers …" stayed in connected_load;
      "Total connected load" kept a stale circle. `_switch_dataset` now scores by
      matched key-token count and only switches to a STRICTLY better match; a
      multi-word subject drops the inherited entity; count/number→connection,
      load/kw→connected_load hints added.
    - **Row-wise metric**: "Domestic count circle wise" ignored the named column
      (gave Total). Row-wise now honours a metric named in the same message.
    - **Superlative category**: "maximum domestic consumers" ranked Total, not
      Domestic. `_superlative_answer` now ranks by an explicit category when named.
    - **Comparison**: bare "Difference?" wasn't recognised (added `_DIFF_RE`);
      `_recent_facts` now stops at the two most-recent entities so a comparison
      isn't polluted by a row mentioned several turns earlier.

11. **Residual conversational fixes (3rd UAT round)** — closed the two known
    residuals:
    - **Prose→numeric hijack**: after a prose answer ("security deposit" rates),
      an elliptical "for domestic?" was grabbed by the numeric path (returned the
      domestic connection COUNT). Fix: `followup.is_prose_followup` (last answer was
      substantive prose + this is elliptical) makes `chat.stream_answer` continue in
      RAG → domestic DEPOSIT rate (Rs.750/KW). Contextualizer gained a prose-subject
      example so the rewrite retrieves well.
    - **Comparison metric switch**: "which has more connections?" right after a LOAD
      comparison reused the KW values. Fix: `followup.compare_answer` detects when the
      question's subject mismatches the recent facts and RE-FETCHES that subject for
      the same entities from SQLite (connection counts 543,445/392,024), instead of
      reusing load. Same-subject comparisons ("which has more load?") still reuse
      history; "which is higher?"/"difference?" unchanged.
    - **Full-transcript replay hardening**: replaying the customer's entire 74-turn
      session caught the prose-anchor detection over-triggering — a comparison RESULT
      ("X has a higher Y than Z") and a numeric CLARIFY ("Which count?") were being
      treated as prose, pushing the NEXT numeric follow-up to RAG (which fabricated
      "2,200,000 KW" for Karnal load). Fix: `_last_answer_was_prose` also excludes
      comparison results (`_COMPARISON_RESULT_RE`) and any answer containing "?" (a
      clarify question), and requires a substantive length. Also: a row-wise query on
      a SWITCHED dataset with no named metric now uses the aggregate ("load circle
      wise" -> Total load per circle, not the prior dataset's Domestic).
    - **Superlative refinement**: after "which circle has the highest damaged
      transformers?" (Karnal Rural), a follow-up naming a sub-group ("what about
      rural?", "and urban?") returned the AGGREGATE row (Total Rural 24,076 / Total
      Urban 1,572). Fix: `followup.superlative_refinement` re-runs the SAME ranking
      restricted to rows matching that cross-cutting sub-label (>=3 rows, so a
      district name is excluded) → top rural circle (Karnal Rural 5,193) / top urban
      circle (Panipat Urban 278); direction (max/min) carried from the prior answer.
    - **Count vs load routing**: "ECS count in Ambala" returned 3,063 KW (from the
      connected-LOAD report) instead of the connection COUNT (45). A category
      (ECS/Domestic/…) exists in both reports; `INTENT_PROMPT` rule 1 now
      disambiguates by unit — count/number/how-many -> connection dataset,
      load/kW/connected-load -> connected_load. Also `tables._dedupe_facts`
      collapses the connection PDF's duplicate 'ECS' column (a real 45 + an empty
      0) to one clean value, applied on the normal, segregation and row-wise paths.
    - **LT vs HT & explicit category**: "panchkula lt industry" returned HT Industry
      (2-char "lt"/"ht" were filtered as noise, so LT/HT Industry & LT/HT NDS were
      indistinguishable) — `_col_tokens` now keeps 2-char tokens. And "other count
      for Zone-II" returned Total instead of the "Other" column — `respond` now lets
      an explicitly-named category override a defaulted aggregate, but ONLY for
      single-selection queries (so "domestic connections and total load" keeps the
      Total for the load part; verified via validate_e2e's compound case).

12. **Abbreviations glossary ingested** — `Haryana_DISCOM_Abbreviations.txt` (255
    entries across 24 categories) added to the prose KB via `add_abbreviations.py`
    (idempotent append, one self-contained chunk per entry, backs up the pkl). The
    bot now answers "what is X / full form of X" for UHBVN/DHBVN terms including the
    RTS Act framework (RTS, Designated Officer, FGRA, SGRA), consumer categories
    (FPO, DMRC, Gaushala, PWW, EHT, Bulk Supply), APPC, MGJGY, OTS, SDO/XEN/JE,
    AT&C, etc. Run `add_abbreviations.py` on prod (dev/prod pkls differ). Verified:
    RTS→Right to Service, MGJGY→Mhara Gaon Jagmag Gaon Yojana, FGRA→First Grievance
    Redressal Authority; eval_rag 7/7 and validate_e2e 0% FP unchanged. A SECOND
    glossary `Electricity_Department_Abbreviations.txt` (146 line-format entries:
    POSOCO, PGCIL, SAIFI/SAIDI/CAIDI, DT/DT Failure Rate, UDAY, PRAAPTI, DAM/RTM,
    IEX, etc.) is ingested via `add_electricity_abbrev.py` (same idempotent pattern).
    The two glossaries do NOT conflict: identical terms reinforce, genuinely
    multi-meaning terms (PT, REC, GIS) return the dominant meaning, and figures
    always come from SQLite — never the prose glossaries. **Deterministic definition
    lookup** (`app/glossary.py`): a definition query ("what is AT&C Loss?", "full
    form of SAIFI", or a bare distinctive term like "AT&C Loss") is answered
    straight from the matching glossary chunk — reliable, so a known term never
    falls through to a numeric clarify or a nondeterministic RAG "could not find".
    Used only as a FALLBACK (after the numeric path + inside prose-continuation), so
    it never overrides a real data answer like "what is the collection efficiency?".
    Extended with: multiple-meaning output for genuinely ambiguous terms (PT →
    Potential + Power Transformer, REC, GIS, ABR); "Who is X?" / "What about X?"
    phrasing; near-duplicate dedup across the two glossaries; and `define_multi` — a
    PURE definition BATCH ("What is ACS?\\nWhat is ARR?\\n…" sent as one message)
    resolves every term deterministically (the RAG multi-question path was
    unreliable, refusing several). A MIXED batch (definitions + "how does it work?")
    is left to RAG. Pronoun follow-ups ("how does it work?", "how are they
    related?") are now contextualised (`_BACKREF_RE` += it/they), and a conceptual
    "what is the difference?" between two defined terms is explained by RAG while a
    numeric difference still computes. **Category listing** (`glossary.list_category`):
    "show safety abbreviations", "list metering terms", "show consumer categories"
    return the exact set from the glossary `Category:` fields — deterministic, fixing
    the RAG hallucination (SE mislabelled "Safety Engineer" instead of Superintending
    Engineer). Requires explicit "…terms/abbreviations/categories" phrasing + a real
    category match, so numeric/follow-up/comparison queries are untouched.

    still returns the glossary definition; DT/transformer clarifications, DSM/GIS
    ambiguity, security-deposit follow-ups, numeric and slot behaviour all unchanged.

16. **RTS "concerned officer" phrasing** — "who is concerned for shifting of meter?"
    asked to specify the service although it was named (JE). The RTS chunk-injection
    trigger (`rag._RTS_TRIGGER`) only matched "designated officer / who is responsible
    / rts"; added "who is concerned / concerned officer / who handles / who deals with
    / in-charge of". Still gated by a required service word, so a bare "who is the
    designated officer?" (no service) still clarifies.

17. **Transformer failure-rate mis-route (wrong data)** — as a follow-up,

18. **Transformer failure-rate "could not find" (data exists)** — a fresh (or
    prose-context) "Transformer failure rate in Ambala" intermittently returned
    "I could not find this information" because the LLM router waffled on the phrase
    "failure rate" (picking the DT count, clarifying, or a not-found). Two smallest
    fixes: (a) in `tables.respond`, normalise `failure rate` → `damage rate` and add
    a DETERMINISTIC route — when the query names transformer/dt/dtr + "damage rate"
    and `damaged_transformers` exists, force the "% Damage rate excluding warranty
    period Total" column ("including" when the user says so), bypassing the LLM;
    (b) a scoped `chat.py` branch (`_TRANSFORMER_RATE_RE`) that, for a transformer
    damage/failure-rate query, calls `tables.respond` on the RAW user input so a
    contextualiser hiccup or a "could not find" prior turn can't derail it. The
    branch runs AFTER the `transformer_domain_switch` guard, so a connection→DT
    follow-up ("DS connection in Ambala" → "DT failure rate in Ambala") still gets
    that guard's clarification (unchanged, still passes eval_followup). "Transformer
    failure rate in Ambala" → "Ambala — % Damage rate … 3.56%".

19. **Definition question hijacked by stale numeric context** — after a numeric turn
    (e.g. a transformer answer/clarify), a single-term definition question ("what is
    PT?", "what is ABCXYZ?") was rewritten by the contextualiser into the active
    dataset and answered with the numeric "I have damaged transformers data, but please
    name the circle or year/period you want." Cause: a bare/unknown term isn't resolved
    by the glossary (short bare tokens are deliberately refused to protect slot words
    like HT/DS/Total), so it fell through to the LLM-contextualised numeric path. Fix:
    a scoped `chat.py` guard (`_ABBREV_Q_RE`) resolves a SINGLE-term "what is X?" /
    "define X" / "full form of X" from the glossary on the RAW input BEFORE the numeric
    slot/contextualise path — known term → its definition; an explicit but UNKNOWN term
    → RAG (a clean "could not find"), never the numeric clarify. Narrow by design (the
    subject must be a single token), so numeric "what is the collection efficiency?" and
    multi-word terms ("what is AT&C Loss?", still handled downstream) are untouched. All
    slot follow-ups ("Total?", "Domestic?", "Zone-I?") and known glossary answers
    unchanged.

20. **Conceptual "difference between X and Y" reused stale numbers** — in a chat where
    an earlier numeric comparison left figures in history (e.g. "Compare HT and LT" →
    HT-Lines), a later CONCEPTUAL "difference between SLDC and RLDC" (or "OA and PPA")
    wrongly answered "The difference in HT Lines … is 12,226", comparing unrelated
    numbers. Fix: `followup.compare_answer`, when the question names a SUBJECT the recent
    facts don't cover AND it can't be re-fetched from SQLite, now returns None instead of
    comparing the mismatched history → the caller explains the difference conceptually via
    RAG (SLDC vs RLDC, OA vs PPA). Quantity-framing words ("how", "much", "many") were
    added to the comparison stop-list so "how much difference?" isn't misread as a
    subject. All numeric comparisons (which-is-higher, re-fetch of a different metric,
    exact difference) are unchanged.

21. **Bare ambiguous abbreviation returned only one meaning** — typing just "GIS" or
    "REC" gave a single meaning (via RAG), not both. `glossary.define` deliberately
    refuses short bare tokens (to protect slot words like HT/DS/Total), but now makes an
    EXCEPTION for a token with ≥2 distinct meanings (PT, GIS, REC) — those aren't slot
    dimensions, so returning the full disambiguation ("PT can refer to: … / …") is safe
    and matches intent. Single-meaning short tokens (HT, LT, DS, OA) stay refused, so slot
    follow-ups are untouched.

13. **Deterministic count-vs-load routing** — "ECS/lift-irrigation/domestic in X"
    (a category living in BOTH the connection-count and connected-load reports)

## 1. The problem (root cause)

The original bot had **one retrieval path**: it split every source document into
fixed-size text chunks, embedded them, and answered every question — including
questions about **numeric tables** — by vector similarity.

UHBVN operational reports (e.g. `1_Connection.pdf`) are **positional tables**:
the connection report has **23 columns**, where the value `3,003,464` only means
"Domestic" because of its column position. When such a table is flattened to text
and cut into 1,000-character chunks, the column header is severed from its value.

Result (the 3 reported issues):
1. "How many connections" returned **3,003,464** (the *Domestic* column) instead
   of **3,892,250** (the *Total* column).
2. "connections and total load" → "I don't have information" (the two values were
   in different chunks; nothing matched).
3. Risk of returning the wrong **row** when similar entries exist (no row filter).

**Conclusion:** a table-extraction + chunking problem, not an embedding or model
problem. Hallucination was a *symptom*.

## 2. The fix in one picture: two retrieval paths + a router

```
                        user question
                              │
                ┌─────────────┴──────────────┐
                │   tables.respond(question)  │   (router, app/tables.py)
                └─────────────┬──────────────┘
        numeric / table Q?    │     procedural / policy Q?
        ┌─────────────────────┴───────────────────────┐
        ▼                                               ▼
 STRUCTURED STORE  (SQLite, exact lookup)        VECTOR RAG  (circulars)
 - deterministic value, never via the LLM        - top-K chunks + LLM
 - (Source, Row, Column) citation                - temperature 0, cite circular
 - "Data not found" if absent                    - forbidden from inventing figures
```

- **Numbers** now come from exact cell lookups (cannot be hallucinated).
- **Policy/procedure text** still comes from the LLM over retrieved circulars,
  now with guards so it cannot invent charges.

## 5. How the structured path decides an answer

For a numeric question, `respond()` runs:

1. **Procedural guard** — if the text contains procedure/how-to/documents/
   required/charges words, it is NOT a table question → go to prose RAG.
2. **Dataset match** — map keywords to a dataset (e.g. "connection" → connection
   table), restricted to **trusted** datasets only.
3. **Column selection**
   - User named a column (even misspelled) → that column (fuzzy, exact-preferred).
   - Otherwise → the dataset's **default Total** column (this is what fixes the
     Domestic-vs-Total bug).
   - Sibling sub-columns collapse to the aggregate unless explicitly requested
     (e.g. bare "transformer damaged" → Total; "out of warranty" → that column).
4. **Entity (row) selection**
   - District named (with spelling canonicalisation, e.g. Sonepat/Sonipat) → that row.
   - No district → the utility-wide Grand Total row.
   - **Unknown place named** (e.g. "on the Moon") → refuse/clarify, never the Grand Total.
5. **Return** — exact value + `(Source, Row, Column)` citation, OR a clarify
   prompt, OR "Data not found." The number is **never generated by the LLM**.

## 10. Known limits / future work

- **Quarantined datasets** (year-wise series, defaulting amounts, OA-level losses)
  are not answered yet — they need per-layout extractors, then re-pass the trust gate.
- **Dataset routing is keyword-based** and not yet fuzzy — "domastic grand total?"
  with no mention of "connection" goes to prose. Can add dataset-level fuzzy/semantic routing.
- **Multi-question blobs** strain the prose retrieval (top-5 chunks); ask one topic
  at a time, or raise `TOP_K`.
- **Prose answers are best-effort grounded** (LLM over retrieved text); the numeric
  path is the guaranteed-correct one.
- Production deploy checklist: ship `uhbvn_tables.db`, set `ALLOWED_ORIGINS`,
  confirm runtime boots without PyMuPDF, smoke-test, staging before prod.
